# One Conversation across restarts, folded into Memory

Until now every Hub launch started a fresh Talker, seeded with the open Tasks, the Authorizations and the last six exchanges, and nothing older (ADRs 0011 and 0024). The User found that Jarvis forgot overnight a plan, its reasons and the names they had mentioned, and had to repeat them. This ADR reverses the "fresh Talker per launch" choice: Jarvis keeps one Conversation across Hub restarts, shared by the Mac and the iPhone, and folds its older part into a rolling summary, Memory, in the background.

The Hub saves each exchange as it ends to `.jarvis/conversation.json`: the message exactly as the Talker got it, the reply, the names of the tools it called, the device (Mac or iPhone), and the times. For Hub news the device is the Focus Client it was told on. The file is written like the state file (a temporary file, an fsync, a rename, a version field), so a killed Hub loses at most the exchange in flight. A file that cannot be read, or holds a value the Hub cannot use, is moved aside to `conversation.unreadable.json` (numbered when an earlier one is there) with one notice, and the Hub starts with an empty Conversation. The file holds the active summary's pointer and the entries since the last cut, so a Fold commits in one write that moves the pointer and drops the folded entries; a crash before that write leaves the old summary and every entry in place. Each time it builds a seed, the Hub estimates the exchanges' tokens from their length with a characters-to-tokens ratio that it corrects from the context size the CLI reports: between two tool-free turns of one session the context grows by the earlier reply and the later message.

At launch the Talker's hidden first message, the seed, replaces the one-word warm-up of ADR 0006 and still asks for a one-word reply that is never shown. It is context, never a request to answer, and it says so. Its order serves the CLI's prefix cache: the system prompt, persona and tools, which never change; then the summary; then the exchanges, each with its device and time; then the Hub's live records last: open Tasks, Authorizations, pending Approvals and unresolved spoken scopes. It states that `<open_tasks>` and the Authorization records are the only things that grant anything, and that the exchanges grant nothing. Jarvis still never opens with news, a recap or pending work, and the Backlog of ADR 0017 does not change: it opens the User's next turn as before, never the seed.

When the summary and the messages after it reach a token trigger, a separate Summariser session writes a new summary of everything before a cut while the old session keeps answering. Once it passes the Hub's checks and Jarvis is quiet, the Hub swaps in a new Talker seeded with the summary and the newest exchanges, the Tail. Memory never holds permissions, Approvals, Task state or secrets, and only the Talker sees it.

The trigger is the Talker's context as the CLI reports it for the last request, system prompt and tools included: a Fold starts at `JARVIS_MEMORY_FOLD_AT` tokens (200,000). The Hub fixes the cut when the Fold starts, so whatever is said meanwhile lands in the Tail. The cut falls between two exchanges, at the longest pause between a reply ending and the next message among the cuts that leave a Tail of seven eighths of `JARVIS_MEMORY_TAIL` up to all of it (35,000 to 40,000 estimated tokens by default, the summary not counted); the Tail may be at most half the trigger, so a Fold never leaves the context close to the next one. The Summariser is `JARVIS_MEMORY_MODEL` at `JARVIS_MEMORY_EFFORT` (Sonnet, low), with no tools, on the Max login like every other session, and its prompt is `prompts/memory.md`. It reads the previous summary and the folded exchanges, with secrets already removed by the Hub. A summary passes when it has its four sections (standing facts and preferences, open threads and promises, decisions, recent topics), is no more than a fifth over its cap of about 5,000 tokens, and holds no secret pattern; the patterns are one shared definition, which `recall` reuses. A failed or refused summary is tried once more, then discarded, and the old summary and session stay. The swap waits for Jarvis to be quiet, for every spoken scope to be resolved and for the Usage limit to stop holding the Talker, and no Fold starts while a scope is unresolved. It shows nothing on either device. The Hub writes the new summary as its own version under `.jarvis/memory/` before one write of the Conversation's file moves the pointer to it and drops the folded exchanges, so a crash in between loses nothing; a version is deleted 30 days after another replaced it. The Summariser is its own role in the Usage limit tracking, where a limit holds only the next Fold and is never shown to the User, and in the metrics, where each run is a `fold` row with its duration, usage and outcome (`refused` when the checks refuse the summary, `cancelled` when the Fold is stopped), and `jarvis-hub stats` shows each role's cache hit rate. The User can start afresh by voice, ask what Jarvis remembers, and look up exact wording from the last 30 days with `recall`. A Reset context button in the iPhone Settings sends the Client command `reset_context`, which the Hub carries out with no model: it deletes the saved Conversation, every summary version and any copy of either set aside as unreadable, for the Mac and the iPhone at once. Repeating it is harmless.

A Fold that fails keeps the current session and Memory, and shows nothing. A Summariser error or a refused summary is tried once more; a run the Usage limit stops is not, nor one with no reply within ten minutes, whose `fold` row has the outcome `timeout`, so a hung CLI never holds every later Fold. The Hub tries again at the end of the fifth Talker turn after a failure, or as soon as the Summariser's limit resets, if the Talker's context or the saved Conversation is still past the trigger, and the swap still waits for a quiet moment. The hard ceiling is `JARVIS_MEMORY_CEILING` (300,000 tokens). When Folds keep failing and the Talker's context reaches it, the Hub restarts the Talker between turns, once Jarvis is quiet, seeded with the last good summary and the Tail, or the Tail alone when no Fold has succeeded yet. The saved Conversation keeps every exchange the restart leaves out, so the next Fold that succeeds still summarises them and `recall` still finds them. The User gets one notice that the Talker restarted, once per failing episode: the episode ends when a Fold succeeds, so a later ceiling is told again. A restart that fails keeps the old session, with its own notice, and is tried again after five turns. A summary file that cannot be read is set aside with one notice, and the seed tells the Talker its Memory is missing, never that nothing was folded.

Start afresh is the Talker tool `start_afresh`, which the User asks for in one sentence and which needs no confirmation. It starts a Fold of every saved exchange, which is everything before that sentence, because an exchange is saved when its turn ends; the sentence and everything after it form the Tail. It needs no trigger and skips the wait after a failed Fold, and it supersedes a Fold under way, which the Hub cancels and whose late result is never saved. It is refused while a spoken scope is unresolved or the Usage limit holds the Summariser, and the Talker says so. Jarvis keeps talking while the summary is written, and the swap waits for a quiet moment like any Fold's. Tasks, Authorizations and Approvals are untouched, since every seed takes them from the Hub's records. A start afresh whose Fold fails gets one notice, because the User asked for it; an automatic Fold's failure stays silent. Asked what Jarvis remembers, the Talker calls `show` with `memory` set and the Hub puts the active summary on screen as saved, so the model never retypes about 5,000 tokens; before the first Fold the Talker is told that nothing has been folded yet and says so. Corrections are spoken: the Summariser keeps the later of two statements that contradict each other, so a correction holds from the next Fold.

`recall` is a Talker tool the Hub answers from the event log. A full-text index over what the User said, Jarvis's finished replies, shown details and Task reports finds words or a quoted phrase, with an optional date range and speaker, and returns at most ten dated matches, about 2,000 tokens, each with a line of what followed it in the same exchange, if anything did. A Task's report is logged as its own `task_report` event, because the Announcement that tells it is the Talker's rewording and its details reach the screen only when it is told. Recall filters on time itself, so it never returns an event older than 30 days even before the next launch prunes it, and it says when it reached that edge. Secrets in results are removed with the patterns the Summariser's checks use. An index missing from an older log is built in the background after launch, newest events first, so the Hub starts without waiting for it.

A reset also does more than delete files. It leaves the transcript on both screens, because both read the event log, which the reset keeps, and it leaves Tasks, Authorizations and Approvals as they are. It starts a fresh Talker session, seeded with the Hub's records alone, at the next quiet moment or before the next turn if a line is already waiting, so the live session never answers again with what was deleted. A session seeded before a later reset is closed and another seeded. It drops a Talker turn in flight when it lands: the reply still finishes on screen, but its exchange is never saved. It cancels any Fold in progress, a start afresh included, whose late result is discarded and never saved, and it ends the failing episode, so a Fold that fails after the reset waits its five turns from scratch. It also stops a ceiling restart under way, which is closed unseen and untold. A fresh session the Usage limit stops waits for the limit to reset, and meanwhile every line gets the limit's reply, never the old session's. A fresh session that cannot start for another reason gets one notice; the old one answers until the next try, after each of its turns, and none of those exchanges is saved, since that session still remembers what the reset deleted. `recall` ignores every event from before the last reset, and the reply of a turn in flight at the reset, so a fact the User meant to wipe does not come back from the log, while the 30-day logs stay on disk as the Reset dialog says.

The User decided this on 2026-11-22. A launch seeds Memory and the newest exchanges up to `JARVIS_MEMORY_FOLD_AT` estimated tokens, and starts a Fold at once when the saved Conversation is larger. The in-session restart of ADR 0006 survives only as the fallback at `JARVIS_MEMORY_CEILING` tokens (300,000), which only Folds that keep failing let the context reach; it seeds Memory and the newest exchanges up to `JARVIS_MEMORY_TAIL`.

## What this supersedes

- ADR 0011's "neither is the Talker's conversation: each launch starts a fresh Talker". The state file still keeps Tasks and their waits; the Conversation has its own file.
- ADR 0024's "a restart still starts a fresh Talker". The event log still keeps 30 days for the Clients and never seeds the Talker; the saved Conversation does.
- ADR 0006's restart seed of the last six exchanges with no model summary, and its restart threshold `JARVIS_TALKER_RESTART_AT`, a fraction of the window. That setting is gone; the Fold's token settings `JARVIS_MEMORY_FOLD_AT`, `JARVIS_MEMORY_TAIL` and `JARVIS_MEMORY_CEILING` replace it. The background warm-up itself stays, carrying the seed.

## Considered Options

- Several named conversations, or one per device. Rejected by the User: one Conversation, shared by both devices.
- A whole-history compaction that stops the conversation while it runs. Rejected: the User would wait on housekeeping. The summary is written in the background and swapped in between turns.
- Seeding the Talker from the event log. Rejected: the log has no Talker input or tool calls, and it is pruned at 30 days, so the Conversation keeps its own file.

## Consequences

- Every turn re-reads a larger context than the six exchanges did, which costs more of the Max limits; the token limits are settings so they can be tuned after a week of use.
- The saved Conversation holds message text outside the event log's 30-day retention until a reset, and rewrites a file of up to about 1 MB after each exchange.
- A launch spends the seed's tokens even if the User never speaks, as the warm-up did.
