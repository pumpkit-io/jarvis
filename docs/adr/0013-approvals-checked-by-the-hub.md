# The Hub decides an Approval from its own record, and runs merges and branch deletes itself

ADR 0004 made the User's yes a recorded Approval. This records how the Hub decides that a yes counts, how it carries out what it can, and how far a Subagent's tools widen for the rest. The code is `src/jarvis_hub/approvals.py`.

## Asking

The Orchestrator asks through `report(..., approval={...})`, naming one action from a closed set: `merge_pr` (repo, PR number, head commit), `delete_branch` (repo, branch, tip commit) or `subagent_action` (`grants` naming connector tools from a closed list, and a description of the one exact action; for an X post the request names the post, `post_action`, `publish_at` for a schedule and any `community`, and the Hub writes the description itself from them, so the User hears exactly what the grant allows). Before the User hears anything, the Hub reads the target with gh and refuses a commit that is not current, so the User is asked about the PR as it is. The screen shows the exact action in the Hub's words, and the event carries `approval="A1"`. A newer request on the same Task withdraws the one pending, and cancelling the Task withdraws them all. The request is news that needs the User, so it gets through Quiet mode once per change (ADR 0012).

## When a yes counts

The Talker's `approve(approval_id)` takes only the id. The Hub, not a model, decides whether the User said yes and to what, from the `<user>` line in its own record of the turn. The rule lives in `Approvals.decide`, with the lexicons as data files in `src/jarvis_hub/approval_lexicons/`. It accepts when:

1. the Talker turn answers a `<user>` message, spoken or typed, and no other Approval was approved in that turn;
2. the words are a plain yes. They hold a yes from `yes.txt` ("yes", "go ahead", "do it", "sì", "procedi", "fallo") or a verb of the action from `verbs.txt` ("merge it", "Merge forty-two"), and every other word belongs to a closed set: the action's own verbs; words that name its target (the PR number in digits or number words, optionally after "number", plus "PR" or "pull request" for a merge; the branch, its last part and "branch" for a delete; the repo name, alone or with "repo"; a phrase made only of yes, filler, verbs or "now" names nothing, so "Yes, Jarvis." never names the branch feat/jarvis and "go ahead" never names go-ahead); "now", only for an action that runs at once, so never for a scheduled post; and the filler in `filler.txt` ("please", "it", "the", "and", "sir", "jarvis", "ok", "go", "ahead", "do", "per favore", "grazie", "signore", "pure", "la"). One word outside it refuses: "Sure, abort.", "Yes, in an hour.", "Merge it next week.", "Go away." and "Post it on Friday" (for a post now) all do. The hold lexicon stays as a second check: a phrase from `hold.txt` ("no", "not", "wait", "later", "but", "non", "aspetta", "dopo"), a word ending in n't, or a question mark refuses too. Both fail closed, and the refusal names the word, says nothing was done, and gives a plain yes to ask for, such as "yes, merge 42". A plain yes that happens to hold an unlisted word ("yes, merge it right away") is refused by design: the Talker asks again, and one more sentence from the User costs less than a yes the words did not mean;
3. the last turn Jarvis finished asked about that Approval: its news carried the request, or, after a refused `approve`, the Talker's reply named it. "Named" means the Hub found the Approval's target in the reply, by the same matching as below. A refusal for a "no" opens no read-back, so "No." followed by "I won't merge 42, sir." and a "yes" approves nothing. A turn cut short asked about nothing, since the User may not have heard it;
4. the words choose it, when more than one Approval was last said, or more than one is pending and the request reached the User as news rather than as a read-back. The Hub matches the words against each candidate's targets: the PR number, in digits or as English or Italian number words up to 999 ("forty-two", "quarantadue"); the branch name or its last part ("old idea"); the repo; and the action verb ("merge", "delete", "post", "schedule"). A word can't be both a yes or filler and a name: "Jarvis" alone is the User addressing Jarvis and never names the jarvis repo (that takes "the jarvis repo", "repo jarvis" or the PR number), and "it", "please" or "the one" never name a branch spelled that way. Numbers are ASCII digits or number words; other digits, such as "²", are a word outside a plain yes. A target counts only when no other candidate shares it, so "merge" names a merge only when one candidate is a merge. The words must name exactly the Approval the Talker passed, or the Hub refuses and names the one they did. After a refusal, a reply that reads back exactly one Approval makes it the only one last said, and a plain yes then counts for it;
5. the words name nothing else: a number, verb, branch or repo that belongs to another pending Approval or not to this one ("yes, merge 43", "yes, delete it" for a merge) refuses.

Otherwise the result lists every pending Approval where the User has to choose, and the Talker names them and asks which. The words stored with the Approval are the `<user>` line from the Hub's own record of that turn, never anything in the tool call. The record of what was last asked is not saved: after a restart the first yes is refused and the Talker names what is pending, at the cost of one more question.

An Approval is single-use and expires 24 hours after it was asked, on the Hub's clock. Right before acting, the Hub reads the target again: a PR that is no longer open, or whose head moved, and a branch that is gone or moved, lapse the Approval. Nothing runs, and the Orchestrator gets an event saying what changed so it asks again.

## What the Hub runs

Merges and branch deletes run with a fixed argv, no shell, behind ADR 0007's `env -i` (gh signs in from its own config and the keyring, as for reads), and each run is logged to the metrics with the argv, exit code, output and the User's words:

- Merge: `gh pr merge <n> -R <org>/<repo> --merge --match-head-commit <sha>`. The Org's repos merge with a merge commit, and GitHub refuses the merge if the head is no longer that commit, so the re-read is backed by GitHub itself. A repo set to delete head branches on merge still does so: that is its own setting, not the Hub's act.
- Branch delete: GraphQL `updateRefs` with `beforeOid` set to the approved tip and a zero `afterOid`, which GitHub applies only while the ref still points there. The repository's node id comes from the same read that checks the tip. `gh api -X DELETE` was rejected: it deletes whatever the branch points at by then.
- The default branch and protected branches are never deleted. The GraphQL read also returns the repository's `defaultBranchRef` and whether a classic `branchProtectionRule` or `refUpdateRule` covers the branch. Neither field sees a ruleset: on 2026-11-04 pumpkit's `main` had an active repository ruleset with a `deletion` rule, and both read null. So the Hub also reads `gh api --paginate repos/<org>/<repo>/rules/branches/<branch>`, every page of it, which lists the active rules of every ruleset on the branch, and counts it protected when any is `deletion` (deleting is forbidden outright), `non_fast_forward` (a delete is the last non-fast-forward update, and GitHub's classic protection blocks both together) or `update` (the branch is locked against any change). Rules such as `pull_request` or `required_status_checks` govern changes to a branch, not whether it may exist, so they do not count. A rules read that fails refuses, except GitHub's 403 for a private repo on GitHub Free ("Upgrade to GitHub Pro or make this repository public"), where no ruleset is enforced. The Hub refuses the request for such a branch, and an Approval whose branch became default or protected after the yes lapses at execution.

A merge GitHub refuses still spends the Approval; the event says why. An approved action a restart cut off runs again on the next launch, re-read first, so one that already happened lapses rather than runs twice. Every Approval loaded from the state file first passes the same checks as a fresh request (an Org repo, a branch name git accepts, a full commit, an action and grants from the closed sets); one that fails is dropped with a notice and never runs. The Orchestrator's read-only guard is unchanged: it still cannot merge or delete.

## What a Subagent gets

On a yes to a `subagent_action`, the Orchestrator is told and starts a Subagent with `approval_id`. The Hub hands that Approval to that one Subagent: its brief ends with an `<approval>` block holding the id, the exact action and the User's words, and its connector check (ADR 0008) also allows the tools of the Approval's grants. The first such call spends the Approval, after which the check denies them again; it denies them too once the Approval expires, and the Approval is spent when the Subagent ends, whatever it did. The grants are a closed list: `x_post` opens one Pumpkit tool under both its server names, the one the request names in `post_action` (`post_now` or `schedule_post`, so a yes to schedule a post never posts it at once), and only with the exact arguments the Approval recorded when it was asked: the `post_id`, the `publish_at` of a schedule (the same instant, in any UTC offset), the `community` or none, and `share_with_followers`. Any other value, or any other argument, is refused, so a yes to "Friday at nine on the profile" never schedules Saturday or into a community. The Subagent's brief lists those arguments. `x_post` is granted alone, and its request carries no description of the Orchestrator's: the Hub writes it, so a description saying "schedule for Friday" on a `post_now` cannot happen. `posthog_config` opens PostHog's `exec`. A deploy or release needs no connector, so only the written Boundary holds its Subagent to the one action, as ADR 0004 says.

## Considered Options

- Accept a yes when exactly one Approval is pending, and otherwise never. Rejected: with two pending, nothing could be approved until one expired. A yes that names the action, after Jarvis named them all, chooses safely.
- Let the Talker judge whether the User agreed and to which Approval, and refuse only a bare yes. Rejected: "No, don't merge it" approved a merge, and "merge forty-two" approved a branch delete when the Talker passed the wrong id. The Hub now judges both from the words.
- Accept a yes found anywhere in the words unless a deny-list of hold words appears. Rejected: no deny-list is complete, and "Sure, abort.", "Ok, scratch that." and "Merge it next week." approved. The closed set refuses any word it does not know, at the cost of some false refusals.
- Let the Talker pass the User's words to `approve`. Rejected: the model could write words the User never said.
- Keep a Subagent's widened tools open until it ends. Rejected: one X post approved would allow several.

## Consequences

- An `x_post` Approval pins the post id, not its text: an edit in the web app between the yes and the call goes out as edited.
